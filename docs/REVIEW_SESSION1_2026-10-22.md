## 2. Критический дефект (исправить в БЛОК 0)

### C1. Ложное «файл повреждён» делает приложение неработоспособным

`ModelManager.checkInstalledState()` (`origin/main`, строки 117-140) требует **точного** равенства
`file.length() == expected`, где `expected` берётся из `headContentLengths` или, если там пусто,
из манифеста (округлённые `71600000`, `211000000`, `113000000`, `1400000`, `155000`).

Порядок вызовов в `init`:

```kotlin
init {
    checkInstalledState()        // HEAD ещё не выполнен → сравнение с округлёнными числами
    scope.launch { fetchHeadSizes() }   // сеть, асинхронно
}
```

Реальные размеры файлов на HF не равны этим круглым числам (211 000 000 vs фактическое значение
в байтах). Последствия:

1. **Каждый холодный старт** — `checkInstalledState()` возвращает `false` и ставит
   `ModelDownloadState.Error("Файл … повреждён, скачать заново")`. `MainActivity:70` в этом
   состоянии показывает `ModelSetupScreen` вместо книги.
2. Внутри `playText()` тот же вызов (`:229`) даёт «Модель не загружена» даже с валидными файлами.
3. **Офлайн приложение не работает вообще**: HEAD никогда не проходит, `headContentLengths`
   пуст, ложное «повреждён» навсегда. Это прямое нарушение требования «полная работа в
   авиарежиме после загрузки модели».
4. `fetchHeadSizes()` вызывается из каждого экземпляра `ModelManager` (ViewModel + сервис) —
   до 20 HEAD-запросов к Hugging Face при каждом запуске, включая повторные.

Что нужно:
- сохранять полученные HEAD-размеры в `SharedPreferences` (`size:<path>` + `revision`), а не
  только в памяти;
- пока размеров нет — принимать файл, если он в пределах **±2 %** от манифеста (не точное
  равенство); «повреждён» — только при явном расхождении (`< 90 %` или `> 110 %`);
- `checkInstalledState()` не должен требовать сети вообще; HEAD — фоновая оптимизация с TTL
  (например, раз в 7 дней), а не условие работоспособности;
- в `init` порядок: сначала загрузить сохранённые размеры → потом проверять файлы → потом HEAD.

## 3. Замечания

### M1. Сессия 1 изменила формулу синтеза «заодно» (это была задача сессии 2)
`SupertonicEngine.kt` теперь: `duration = rawDuration * 1.05f + 0.18f`, плюс fallback
`codePoints.size / 14.0f + 0.25f`. Эталон — `dp / speed`, без коэффициентов. То есть старая
эвристика (`×1.10 + floor`) заменена новой (`×1.05 + 180 мс`), а не убрана; параметр `speed`
по-прежнему не используется, `Random()` на каждый чанк остался, выход вокодера по-прежнему
обрезается по `targetSampleCount`.

Риск: «проглатывание» могло смениться другим дефектом (дрожание темпа, хвостовая тишина
~180 мс на каждой фразе при 250-символьных чанках = до 3-4 с тишины на минуту речи).
Требование: в сессии 2 **явно откатить** эти коэффициенты, а не «настроить» их.

### M2. Экспорт по-прежнему держит всю книгу в Java-куче
`SupertonicPlaybackService`: `val pcmChunks = mutableListOf<ByteArray>()` → для 3:20 это ~1 ГБ
в куче (лимит 256–512 МБ) → OOM. Плюс контейнер пишется во время синтеза: при отмене остаётся
битый файл. Это ожидаемо (задача сессии 3), но до неё нужен guard: отказ при оценке > 400 МБ.

### M3. Чтение всё ещё копит всю книгу PCM в куче
`sessionChunkMap: ConcurrentHashMap<Int, PcmChunk>` + `PcmChunk(pcmBytes: ByteArray)` — весь
синтезированный звук в Java-куче, без бюджета. Это ровно та причина OOM, которая описана в
аудите как C1; устраняется в сессии 2 (`PcmStore` off-heap).

### M4. Мелочи
- нет `abandonAudioFocus()` в `stop()` — сервис продолжает «владеть» фокусом после остановки;
- в `gradle.properties` остался `googleServices.missing.passthrough=true` (плагин удалён);
- `expectedSizeBytes` для `duration_predictor.onnx` и `voice_styles/*.json` не сверены с
  фактическими (1,4 МБ и 155 КБ — оценки), при строгом сравнении это те же ложные срабатывания;
- в отчёте «строгая сверка размеров» подана как достижение, хотя именно она — источник C1.
